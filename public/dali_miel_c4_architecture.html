C4 · Deployment / DevOps View

Flujo de desarrollo y producción

Lovable acelera la construcción; GitHub controla qué entra a producción. Render despliega únicamente lo aprobado.

1. LovableIteración visual y generación de código.
2. developRama conectada a Lovable para desarrollo.
3. Pull RequestRevisión humana de diff y cambios.
4. CILint · Typecheck · Tests · Build.
5. mainÚnica rama autorizada para producción.
6. RenderAuto deploy después de checks correctos.
7. mieldali.coHTTPS + custom domain + producción.

Preview

Los Pull Requests deben poder validarse en una URL temporal antes del merge.

Database changes

Migraciones de Supabase versionadas en GitHub. Evitar cambios manuales irrepetibles en producción.

Rollback

Git + historial de deploys permiten volver a una versión estable si una liberación falla.

Checkpoint técnico antes de elegir el tipo de servicio en Render: confirmar package.json y el modo de build real. Si el proyecto termina como SPA/estático → Render Static Site. Si el template actual usa SSR/server runtime (por ejemplo TanStack Start en modo servidor) → Render Web Service. La arquitectura de negocio no cambia; cambia únicamente el runtime de despliegue.

Architecture Decisions

Principios que no queremos romper

Estas decisiones funcionan como mini ADRs y ayudan a que el proyecto no pierda dirección cuando crezca.

01
GitHub manda en producciónLovable no publica directamente a main. Todo cambio pasa por PR y CI.
02
Backend mínimo, no backend inexistenteLa UI puede ser ligera, pero pagos y totales siempre se validan server-side.
03
Productos fuera del códigoPrecio, stock, SKU y estado viven en PostgreSQL, no hardcodeados en componentes React.
04
Checkout como invitadoNo bloquear conversión obligando a crear una cuenta. Auth se reserva inicialmente para administración.
05
Pasarela desacopladaWompi sirve para Sandbox, pero el dominio de pagos expone una interfaz propia para cambiar proveedor sin rehacer la tienda.
06
Webhook = autoridad de pagoLa redirección del navegador no marca pedidos como pagados; solo un evento verificado del proveedor.
07
Secrets nunca en frontendservice_role, llaves privadas y secretos de eventos viven en Supabase Secrets/entorno servidor.
08
Infraestructura proporcionalRender + Supabase cubren el caso actual. No introducir microservicios, colas o Kubernetes hasta que exista un problema real que los justifique.
